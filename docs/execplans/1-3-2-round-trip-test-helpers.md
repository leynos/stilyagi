## Purpose / big picture

Roadmap item 1.3.2 adds the internal test scaffolding that later feature slices
need before Stilyagi can trust source spans, flattened `segments`, diagnostics,
and safe edits. After this work, maintainers should be able to add a fixture to
the shared validation corpus, generate or update a golden intermediate
representation (IR) snapshot, assert command-line interface (CLI) output, and
prove that fix edits round-trip through source text without corrupting spans or
synthetic content.

This slice is deliberately a scaffolding slice. It should make regression tests
cheap and repeatable, but it must not publish the future pytest plugin proposed
by Request for Comments (RFC) 0004. The observable outcome is a private Rust
and Python test-support layer, representative golden files or snapshots, and
tests that prove those helpers catch span, `segments`, diagnostics, and edit
drift.

## Context and orientation

The repository is a mixed Rust and Python project. Rust crates live under
`crates/`, Python package code lives under `python/stilyagi/`, Python tests
live under `tests/`, shared source fixtures live under
`tests/fixtures/corpus/`, and Python behaviour-driven development (BDD) feature
files live under `features/`. The Rust bridge crate `crates/stilyagi-pyext/`
contains the PyO3 extension that Python calls.

Roadmap item 1.2.2 has already created the first Rust-to-Python extraction
call. That bridge is intentionally narrow today:
`stilyagi.engine.extract_document` can return a typed Python document for
Markdown, while the Rust-to-Python payload currently exposes `syntax` plus
regions with `kind` and `text`. It does not yet expose the full target IR shape
with `line_index`, `segments`, owner metadata, or canonical IR JSON.

Roadmap item 1.3.1 has already created the shared source corpus under
`tests/fixtures/corpus/`, with Markdown, Python, and Rust examples split into
valid and malformed groups. Python docstring and Rust documentation-comment
fixtures are source inputs for later extractor work; they are not a promise
that those extractors work yet.

The current implementation touchpoints are:

- `crates/stilyagi-ir/src/lib.rs`, currently a marker crate, is the natural
  place for private IR data transfer object (DTO) types and canonical
  serialization helpers if this slice needs them.
- `crates/stilyagi-extract/src/lib.rs` owns `ExtractDocument`,
  `ExtractRegion`, `ExtractError`, `ExtractSyntax`, and `extract_document`.
- `crates/stilyagi-pyext/src/lib.rs` serializes the Rust extraction result into
  the Python extension payload.
- `python/stilyagi/engine/extraction.py`, `python/stilyagi/model/document.py`,
  and `python/stilyagi/model/region.py` adapt the bridge payload into the
  supported Python model layer.
- `python/stilyagi/cli.py` is currently a placeholder CLI module; any snapshot
  work must avoid implying a broad stable command contract before the CLI
  actually exists.
- `python/stilyagi/diagnostics.py` and `python/stilyagi/engine/fixes.py` are
  minimal placeholders for diagnostics and fix planning. Round-trip helpers may
  use private test DTOs before these become a public API.
- `crates/stilyagi-test-support/src/lib.rs` already provides repository-root
  and corpus-fixture path helpers for Rust tests.
- `tests/test_corpus.py` already provides Python-side corpus discovery and
  BDD coverage patterns.

Definitions used in this plan:

- IR means intermediate representation: Stilyagi's source-faithful document
  payload used to connect extractors, rules, diagnostics, and fixes.
- Golden IR means a canonical checked-in expected IR output for a corpus
  fixture. A test compares current output to this golden output.
- Snapshot means a checked-in expected output generated by a snapshot testing
  tool such as `insta` for Rust or `syrupy` for Python.
- Segment means a mapping from flattened prose back to the original source
  bytes, including explicit representation for synthetic inserted text.
- Synthetic span means text that exists in a flattened or analysed view but was
  not present as an editable byte range in the source file.
- Fix round-trip means applying an edit plan to source text, then checking that
  the changed source, diagnostics, and span mappings are exactly the expected
  result.

## Constraints

- Do not implement this plan until it is explicitly approved.
- Do not publish the RFC 0004 pytest plugin in this slice. Keep Python helpers
  internal to tests or private package modules that are clearly not exported as
  a pytest plugin.
- Do not expose a public Rust or Python IR API merely to support tests. Prefer
  private helper modules, private crate modules, or the existing
  `stilyagi-test-support` dev-only crate.
- Do not claim Python docstring or Rust documentation-comment extraction works
  unless this slice actually implements and tests those extractors. The likely
  first golden IR scope is Markdown plus source-fixture loadability for Python
  and Rust.
- Preserve the current supported Python surface unless the implementation plan
  is revised and approved. `stilyagi.engine.extract_document` remains the
  supported extraction adapter; raw PyO3 dictionaries remain internal bridge
  detail.
- Golden IR must use canonical JSON where JSON output exists. Tests should
  compare parsed structured data or stable serialization, not brittle ad hoc
  string fragments.
- Snapshot tests must avoid machine-specific paths, timing, environment
  values, non-deterministic ordering, and terminal colour output unless those
  values are explicitly redacted or normalized.
- Fix round-trip helpers must reject edits that target synthetic spans and
  must reject overlapping non-identical edits. They must preserve source text
  outside the edited ranges.
- Use `rstest` for Rust unit tests, `pytest` for Python unit tests,
  `rstest-bdd` for Rust behaviour tests, and `pytest-bdd` for Python behaviour
  tests where behaviour is exercised.
- Use `insta` for Rust snapshots and `syrupy` for Python snapshots where output
  format consistency is relevant.
- Use `proptest` for Rust or `hypothesis` for Python only where the
  implementation introduces an invariant over a range of inputs. For this
  slice, the most likely property-test target is edit application preserving
  unedited source ranges and rejecting invalid range orderings.
- Do not introduce formal verification with Kani, CrossHair, or Verus unless
  there is a substantive invariant that is better proved than tested. A proof
  that merely restates helper assumptions is not acceptable.
- Run Makefile gates sequentially and capture long command output with `tee`
  into `/tmp` logs.
- Use `coderabbit review --agent` after each major implementation milestone
  and resolve all actionable concerns before moving to the next milestone.
- Commit each approved, gated change as a focused commit. Do not commit code or
  documentation that fails required gates.
- On completion of the implemented feature, update `docs/roadmap.md` to mark
  item 1.3.2 done. Do not mark it done while this plan is still a draft or
  while implementation is incomplete.

## Tolerances

- Scope: if implementation needs more than twenty files or roughly 900 net new
  lines, stop and explain why before continuing.
- Public API: if any public Rust or Python API signature must change, stop and
  request approval.
- CLI contract: if meaningful CLI command behaviour must be implemented beyond
  the minimum needed to snapshot an existing or newly introduced command, stop
  and present options.
- Dependencies: adding `insta`, `syrupy`, and `hypothesis` is expected if they
  are not already present. Any other external dependency requires approval.
- Golden scope: start with the shared Markdown fixture and at most one
  malformed Markdown case. If broader Python or Rust extraction golden coverage
  is required before their extractors exist, stop and request clarification.
- Runtime: the new helper and snapshot tests should not add more than ten
  seconds to a warm `make test` run on the development machine. If they do,
  document the cause and ask whether to narrow the initial corpus.
- Snapshot churn: if a snapshot requires broad redaction or custom serializers
  that hide most meaningful fields, stop and redesign the payload instead of
  approving a weak snapshot.
- Property tests: keep generated cases bounded and deterministic. If a
  property test becomes flaky or slow after two focused fixes, remove or narrow
  it and document the trade-off.
- Validation: if `make check-fmt`, `make lint`, or `make test` still fails
  after two focused correction passes, stop and record the failing log paths in
  this plan.
- Review: if `coderabbit review --agent` raises a concern that conflicts with
  this plan, record the conflict in `Decision Log` and ask for direction before
  changing scope.
- Ambiguity: if multiple valid helper locations or data schemas remain after
  reading the relevant source, document the options and ask before proceeding.

## Risks

- Risk: golden IR could freeze the current intentionally partial bridge shape
  instead of the target IR contract. Severity: high. Likelihood: medium.
  Mitigation: define canonical golden IR as a test contract over private DTOs
  or debug JSON, not as the raw PyO3 payload.

- Risk: CLI snapshots could accidentally promise a stable user command before
  the CLI slice exists. Severity: high. Likelihood: medium. Mitigation:
  snapshot only explicit help or debug commands created in this slice, document
  them carefully, and update `docs/users-guide.md` only for real user-facing
  behaviour.

- Risk: fixture snapshots could become brittle because paths, ordering, or
  formatting differ across Linux, macOS and Windows. Severity: medium.
  Likelihood: medium. Mitigation: normalize paths to repository-relative
  POSIX-style strings, sort file lists, disable colour, and redact volatile
  fields through `insta` or `syrupy`.

- Risk: fix helpers could validate happy-path edits while missing dangerous
  overlap or synthetic-span cases. Severity: high. Likelihood: medium.
  Mitigation: start with explicit unit tests for rejected synthetic edits,
  rejected overlapping non-identical edits, accepted adjacent edits, and
  preservation of untouched source ranges.

- Risk: adding snapshot dependencies could expand the build spine more than
  intended. Severity: medium. Likelihood: low. Mitigation: add only test/dev
  dependencies, keep them out of runtime dependency surfaces, and document why
  they are present.

- Risk: implementing helper abstractions before the real rule engine exists
  could create a bespoke test framework that later fights RFC 0004. Severity:
  medium. Likelihood: medium. Mitigation: keep helpers small, private, and
  data-oriented. Defer public pytest fixtures such as `stilyagi_path` to the
  later plugin slice.

- Risk: Python and Rust helper surfaces could diverge and produce different
  normalization rules for the same golden data. Severity: medium. Likelihood:
  medium. Mitigation: define canonical JSON ordering and path normalization
  once, then have both languages test that convention against the same fixture
  names.

## Plan of work

Milestone 1 records the exact helper scope in tests before implementation. Add
failing tests for the minimum internal helper surface: a Markdown golden IR
case, a CLI snapshot case for the smallest real command surface, and edit
round-trip cases that cover accepted and rejected edits. The first failing
tests should fail because the helper modules or golden files do not exist, not
because the build spine is broken. Keep these tests focused and name them after
the behaviour they protect.

Milestone 2 creates the private IR test DTO and golden serialization path. If
the existing `stilyagi-ir` crate remains empty, add only the smallest internal
types needed to represent the fields under test: syntax, line index, regions,
segments, diagnostics placeholder data where available, and source-relative
fixture identity. If the current extractor cannot populate full `segments`,
record that explicitly and either create a deliberately partial golden helper
with `segments` marked absent, or implement the minimal Markdown segment
mapping required by section 7.1. Do not expose these types as a public Stilyagi
API unless the plan is revised.

Milestone 3 adds Rust snapshot coverage. Add `insta` as a dev-dependency only
where needed. Use external snapshot files for readable golden IR or command
output, and use redactions or filters for volatile fields. Prefer repository
fixture names and stable JSON over line-number-sensitive prose. Add an `rstest`
unit test that uses the shared Markdown fixture and an `rstest-bdd` behaviour
scenario if the behaviour is clearer in Gherkin than in a unit test.

Milestone 4 adds Python snapshot coverage. Add `syrupy` as a development
dependency if it is not already present. Use `JSONSnapshotExtension` for
structured IR payloads where practical, and reserve raw text snapshots for CLI
output. Keep helper code in `tests/` or an explicitly private internal module.
Do not add a pytest plugin entry point.

Milestone 5 implements fix round-trip helpers. Introduce a small internal edit
model if the existing `Fix` and `FixPlan` placeholders are too public or too
incomplete. The helper should apply source-backed ranges in deterministic
order, reject overlaps unless they are identical and explicitly allowed by the
approved implementation, reject synthetic spans, and return enough structured
data for tests to assert the before text, after text, applied edits, and
rejected edits. Add property tests with `proptest` or `hypothesis` only if they
prove a real range invariant more effectively than examples.

Milestone 6 connects the helpers to the shared corpus without broadening syntax
support. Golden IR should initially target Markdown extraction because that is
the supported bridge path. Python and Rust corpus fixtures should remain
loadable and available for future snapshots, but tests must keep unsupported
extractor behaviour explicit until later roadmap slices implement those
extractors.

Milestone 7 updates documentation. Update `docs/developers-guide.md` with the
new internal helper locations, snapshot update workflow, golden fixture naming,
and fix round-trip conventions. Update `docs/stilyagi-design.md` section 7.1 or
11 if this slice finalizes a canonical test IR helper shape, snapshot directory
layout, or edit safety convention. Update
`docs/rfcs/0004-stilyagi-rule-testing-framework.md` only if implementation
deliberately diverges from the proposed later pytest plugin path. Update
`docs/users-guide.md` only if a user-facing CLI command, API, or output
contract changes.

Milestone 8 validates, reviews, and commits. Run the relevant focused tests as
each milestone lands, then run the full required gates. After each major
milestone, run `coderabbit review --agent`, resolve all actionable concerns,
and record decisions or discoveries in this plan. Once implementation is
complete and gates pass, mark roadmap item 1.3.2 done and commit the final
documentation update.

## Validation and acceptance

- Internal helpers can load shared corpus fixtures and produce canonical
  golden IR output for the approved initial scope.
- Golden IR tests cover source spans and `segments` for at least one supported
  Markdown fixture, or explicitly record and test the approved temporary gap if
  `segments` are not yet implementable.
- CLI snapshot tests pin the approved command output without volatile paths,
  timing, colours, or environment-specific values.
- Fix round-trip tests cover accepted source-backed edits, rejected synthetic
  edits, rejected overlapping non-identical edits, and preservation of
  untouched source ranges.
- Python tests use `pytest`, Python BDD coverage uses `pytest-bdd` where a
  scenario is added, and Python snapshots use `syrupy` where output format

  cover well.

- No new public Rust or Python API is introduced without explicit approval and
  matching documentation.
- `docs/developers-guide.md` documents the internal helper and snapshot

- `docs/stilyagi-design.md` records any finalized IR, snapshot, or edit-safety

## Idempotence and recovery

The implementation should be additive. Re-running tests and validation commands
should not mutate repository state except for ordinary ignored build artefacts,
temporary snapshot review files created by snapshot tools, or `/tmp` logs. If
snapshot update commands create `.new` or equivalent review artefacts, inspect
them, accept only intentional changes, and remove rejected artefacts before
committing.

If a Makefile gate fails, inspect the matching `/tmp/*.out` log first. If the
failure is unrelated to this work, record it in `Surprises & Discoveries` and
ask before widening scope. If the failure is caused by this work, fix it and
rerun only the failed gate before rerunning the final gate sequence.

If snapshot output changes because the helper serialization is unstable,
stabilize the serialization rather than approving churn. If the output changes
because the implementation corrected a source span, segment, diagnostic, or
edit contract, update the snapshot and record the reason in `Decision Log`.

If `coderabbit review --agent` fails for an environmental reason, rerun it once
and capture the log. If it still cannot run, record the failure, include the
log path in this plan, and ask whether to proceed without that review gate.

## Interfaces and dependencies

No runtime dependency is expected.

Expected dependency changes, if not already present:

- Rust `insta` as a dev-dependency in the crate that owns Rust snapshot tests.
- Python `syrupy` in the development dependency group for Python snapshot
  tests.
- Python `hypothesis` or Rust `proptest` only if property tests are added for a
  substantive range or state invariant. `proptest` already appears in the
  `stilyagi-test-support` crate, so prefer reusing that where it matches the
  helper boundary.

Any Rust helper API should stay in `crates/stilyagi-test-support/` or a private
test module unless the production crates need the type for real behaviour. Any
Python helper should stay in `tests/` or a private internal module not exported
from `python/stilyagi/__init__.py`.

A possible Rust-side helper shape is:

```rust
pub struct GoldenIrCase {
    pub fixture_path: &'static str,
    pub syntax: &'static str,
}
```

A possible Python-side helper shape is:

```python
@dataclass(frozen=True, slots=True)
class SnapshotCase:
    fixture_path: pathlib.Path
    snapshot_name: str
```

These shapes are illustrative, not mandatory. Prefer the smallest concrete
types that make tests readable and keep invalid states hard to express.

  Hypothesis coverage, and two byte-oriented helpers did unnecessary repeated
